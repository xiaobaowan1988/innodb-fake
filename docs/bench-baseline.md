# 并发压测基线（优化前：全局 Mutex + 每步重新下探的游标）

环境：4 核机器，压测客户端(pymysql，每个并发一个进程)与 mysqld 共用 CPU；5 万行；autocommit；
InnoDB 设置 `innodb_flush_log_at_trx_commit=2`，buffer pool 128MB（数据全部命中内存）；
每组 4 秒，单次运行，**同机噪声约 ±10%**，只用于相对比较。复现：`scripts/bench.py --socket /tmp/my.sock`。

## 吞吐 QPS（MyEngine / InnoDB）
| 负载 | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| 点查 `id=?` | 4548 / 4701 | 8421 / 8286 | 15885 / 19446 | 14266 / 17806 |
| 范围 100 行 | 1460 / 1706 | 2719 / 2921 | 4591 / 6596 | 4334 / 6424 |
| 二级索引扫描(~500 行+回表) | **887 / 2869** | **942 / 4817** | **784 / 11451** | **757 / 10782** |
| 插入 | 6192 / 1345 | 11954 / 2247 | 15451 / 3345 | 16228 / 4983 |
| 90% 点查 + 10% 更新 | 4724 / 3521 | 8352 / 7355 | 14888 / 14637 | 14240 / 16289 |

## 二级索引扫描 vs 并发（mysqld CPU 占用，100% = 1 核）
| 引擎 | c=1 | c=4 |
|---|---|---|
| MyEngine | 722 qps, CPU 86% | 677 qps, CPU 193% |
| InnoDB   | 2835 qps, CPU 68% | 11348 qps, CPU 254% |

## 结论
- 点查/混合/插入：瓶颈在 SQL 层与网络（每次约 0.18ms），引擎差异被掩盖，MyEngine 与 InnoDB 同量级。
  （插入快于 InnoDB 是因为没有持久化和事务，不是实现更优。）
- 一次要在引擎里做很多步的负载（二级索引扫描、较长范围）明显落后，且**不随并发扩展**：
  MyEngine 加到 4 个并发后吞吐不升反降，p50 从 1.2ms 涨到 5.8ms，而 mysqld CPU 从 86% 涨到 193%
  —— CPU 被消耗但没有换来吞吐，与全局锁争用（多个线程抢同一把 Mutex）一致。
- 单线程下二级索引扫描也慢 4 倍：每行要多次 cgo 调用 + 每步重新从根下探 + 回表再下探一次。

# 第二轮：读写锁 + 游标沿叶子链移动

改动：① 全局 `Mutex` -> `RWMutex`（读并行，写互斥）；游标句柄改用 `runtime/cgo.Handle`（查找无锁）；
② 游标 `Step` 在树未被修改时沿叶子链 O(1) 移动，树被修改（`version` 变化）才按 key 重新下探。
环境、数据、参数与基线完全相同。同一台机器上单次运行噪声约 ±10%。

## 吞吐 QPS：基线 -> 第二轮（InnoDB 供参考）
| 负载 | 并发 | 基线 MyEngine | 第二轮 MyEngine | InnoDB(第二轮) |
|---|---|---|---|---|
| 点查 | 4 | 15885 | 15884 | 18724 |
| 范围 100 行 | 4 | 4591 | 5732 | 6762 |
| 范围 100 行 | 8 | 4334 | 5237 | 6717 |
| **二级索引扫描** | 1 | 887 | 814 | 2747 |
| **二级索引扫描** | 2 | 942 | **1538** | 4917 |
| **二级索引扫描** | 4 | 784 | **2594** | 10594 |
| **二级索引扫描** | 8 | 757 | **2042** | 10238 |
| 插入 | 4 | 15451 | 15198 | 3182 |
| 90% 点查 + 10% 更新 | 4 | 14888 | 15792 | 15585 |

二级索引扫描 c=4：p50 延迟 5.8ms -> 1.4ms，mysqld CPU 193% -> 311%（现在 CPU 能换来吞吐）。

## 消融：两项改动各贡献多少（只开读写锁，关掉叶子链快路径）
| 负载 | 并发 | 仅读写锁 | 读写锁+叶子链 |
|---|---|---|---|
| 二级索引扫描 | 1 | 852 | 814 |
| 二级索引扫描 | 4 | 2359 | 2594 |
| 范围 100 行 | 1 | 1397 | 1502 |
| 范围 100 行 | 4 | 4840 | 5732 |

## 结论
- **读写锁是主要收益**：二级索引扫描在 4 并发下从 784 提到约 2400，约 3 倍，c=1 -> c=4 扩展比 3.2x（InnoDB 3.9x），已基本随核数线性扩展。
- **叶子链快路径收益较小**：范围扫描约 +7%~+18%，二级索引扫描在噪声范围内（+10% 左右）；单线程几乎没有变化。
- **写没有变好**：插入/更新仍需写锁，互斥执行；点查本来就受 SQL 层开销主导，所以不变。
- **单线程二级索引扫描仍比 InnoDB 慢约 3.4 倍（814 vs 2747）**，且这一差距与锁无关，说明主要开销在每行的固定成本：
  每行多次 cgo 调用、`fetch_current` 里每行分配并清零一个 ~600 字节的 `std::string`、回表再下探一次。
  下一步应先 profile 再优化，而不是猜。
- c=4 -> c=8 回落是因为机器只有 4 核且压测客户端也占 CPU。
