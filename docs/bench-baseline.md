# 并发压测基线（优化前：全局 Mutex + 每步重新下探的游标）

环境：4 核机器，压测客户端(pymysql，每个并发一个进程)与 mysqld 共用 CPU；5 万行；autocommit；
InnoDB 设置 `innodb_flush_log_at_trx_commit=2`，buffer pool 128MB（数据全部命中内存）；
每组 4 秒，单次运行，**同机噪声约 ±10%**，只用于相对比较。复现：`scripts/bench.py --socket /tmp/my.sock`。

## 吞吐 QPS（MyEngine / InnoDB）
| 负载 | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| 点查 `id=?` | 4548 / 4701 | 8421 / 8286 | 15885 / 19446 | 14266 / 17806 |
| 范围 100 行 | 1460 / 1706 | 2719 / 2921 | 4591 / 6596 | 4334 / 6424 |
| 二级索引扫描(~500 行+回表) | **887 / 2869** | **942 / 4817** | **784 / 11451** | **757 / 10782** |
| 插入 | 6192 / 1345 | 11954 / 2247 | 15451 / 3345 | 16228 / 4983 |
| 90% 点查 + 10% 更新 | 4724 / 3521 | 8352 / 7355 | 14888 / 14637 | 14240 / 16289 |

## 二级索引扫描 vs 并发（mysqld CPU 占用，100% = 1 核）
| 引擎 | c=1 | c=4 |
|---|---|---|
| MyEngine | 722 qps, CPU 86% | 677 qps, CPU 193% |
| InnoDB   | 2835 qps, CPU 68% | 11348 qps, CPU 254% |

## 结论
- 点查/混合/插入：瓶颈在 SQL 层与网络（每次约 0.18ms），引擎差异被掩盖，MyEngine 与 InnoDB 同量级。
  （插入快于 InnoDB 是因为没有持久化和事务，不是实现更优。）
- 一次要在引擎里做很多步的负载（二级索引扫描、较长范围）明显落后，且**不随并发扩展**：
  MyEngine 加到 4 个并发后吞吐不升反降，p50 从 1.2ms 涨到 5.8ms，而 mysqld CPU 从 86% 涨到 193%
  —— CPU 被消耗但没有换来吞吐，与全局锁争用（多个线程抢同一把 Mutex）一致。
- 单线程下二级索引扫描也慢 4 倍：每行要多次 cgo 调用 + 每步重新从根下探 + 回表再下探一次。

# 第二轮：读写锁 + 游标沿叶子链移动

改动：① 全局 `Mutex` -> `RWMutex`（读并行，写互斥）；游标句柄改用 `runtime/cgo.Handle`（查找无锁）；
② 游标 `Step` 在树未被修改时沿叶子链 O(1) 移动，树被修改（`version` 变化）才按 key 重新下探。
环境、数据、参数与基线完全相同。同一台机器上单次运行噪声约 ±10%。

## 吞吐 QPS：基线 -> 第二轮（InnoDB 供参考）
| 负载 | 并发 | 基线 MyEngine | 第二轮 MyEngine | InnoDB(第二轮) |
|---|---|---|---|---|
| 点查 | 4 | 15885 | 15884 | 18724 |
| 范围 100 行 | 4 | 4591 | 5732 | 6762 |
| 范围 100 行 | 8 | 4334 | 5237 | 6717 |
| **二级索引扫描** | 1 | 887 | 814 | 2747 |
| **二级索引扫描** | 2 | 942 | **1538** | 4917 |
| **二级索引扫描** | 4 | 784 | **2594** | 10594 |
| **二级索引扫描** | 8 | 757 | **2042** | 10238 |
| 插入 | 4 | 15451 | 15198 | 3182 |
| 90% 点查 + 10% 更新 | 4 | 14888 | 15792 | 15585 |

二级索引扫描 c=4：p50 延迟 5.8ms -> 1.4ms，mysqld CPU 193% -> 311%（现在 CPU 能换来吞吐）。

## 消融：两项改动各贡献多少（只开读写锁，关掉叶子链快路径）
| 负载 | 并发 | 仅读写锁 | 读写锁+叶子链 |
|---|---|---|---|
| 二级索引扫描 | 1 | 852 | 814 |
| 二级索引扫描 | 4 | 2359 | 2594 |
| 范围 100 行 | 1 | 1397 | 1502 |
| 范围 100 行 | 4 | 4840 | 5732 |

## 结论
- **读写锁是主要收益**：二级索引扫描在 4 并发下从 784 提到约 2400，约 3 倍，c=1 -> c=4 扩展比 3.2x（InnoDB 3.9x），已基本随核数线性扩展。
- **叶子链快路径收益较小**：范围扫描约 +7%~+18%，二级索引扫描在噪声范围内（+10% 左右）；单线程几乎没有变化。
- **写没有变好**：插入/更新仍需写锁，互斥执行；点查本来就受 SQL 层开销主导，所以不变。
- **单线程二级索引扫描仍比 InnoDB 慢约 3.4 倍（814 vs 2747）**，且这一差距与锁无关，说明主要开销在每行的固定成本：
  每行多次 cgo 调用、`fetch_current` 里每行分配并清零一个 ~600 字节的 `std::string`、回表再下探一次。
  下一步应先 profile 再优化，而不是猜。
- c=4 -> c=8 回落是因为机器只有 4 核且压测客户端也占 CPU。

# 第三轮：profile 驱动的优化 —— 每行只跨一次语言边界

## Profile 方法与发现
- `gdb` 对 mysqld 采样**不可行**（每次附加都暂停进程，吞吐被拖到 31 qps，样本多数落在空闲线程），改用：
  - `bench/microbench.cc`：脱离 MySQL，用与 handler 相同的调用序列驱动 Go 库，逐项拆分单行成本；
  - Go pprof：`MYENGINE_CPUPROFILE=/path/cpu.prof`，调用 `MyEngine_ProfileStop()` 写出。
- 发现（单行二级索引扫描，微基准）：
  - 每次 C++→Go 调用约 130~200ns；旧接口每行 3 次（`CursorStep`+`CursorKey`+`Get`）。
  - 每次 `Get` 还要 `C.GoString(表名)` + map 查表（pprof 里的 `gostring`、`mapaccess1_faststr`）。
  - 回表是随机访问，cache miss 明显（顺序 Get 365ns，按二级索引顺序回表约 700ns）。
  - **每行分配 600 字节 `std::string` 几乎没有成本**（1236ns vs 1261ns，在噪声内）——此前的猜测不成立。

## 改动
新增 `MyEngine_CursorFetch` / `MyEngine_CursorSeekFetch`：Go 端一次完成 移动游标 + (二级索引)回表 + 拷出整行；
C++ 的 `step`、`rnd_next`、`index_read_map`、`index_first/last` 全部改用，每行一次跨语言调用，一次读锁。

## 微基准（每行，3 次重复）
| 接口 | ns/行 |
|---|---|
| 旧：Step+Key+Get（3 次跨语言） | 1017 / 1033 / 1034 |
| 新：Fetch（1 次跨语言） | 654 / 666 / 683 |

## 端到端 QPS：基线 -> 第二轮 -> 第三轮（MyEngine）
| 二级索引扫描 | 基线 | 第二轮 | 第三轮 | InnoDB(第三轮) |
|---|---|---|---|---|
| c=1 | 887 | 814 | **995** | 2648 |
| c=2 | 942 | 1538 | **1858** | 4690 |
| c=4 | 784 | 2594 | **3716** | 9422 |
| c=8 | 757 | 2042 | **3060** | 9954 |

与 InnoDB 的差距（c=4）：基线 14.6 倍 -> 第二轮 4.1 倍 -> 第三轮 2.5 倍。
微基准每行省约 365ns × 500 行 ≈ 0.18ms，与端到端单线程 1.23ms -> 1.0ms 吻合。
点查、范围扫描、插入、混合负载在噪声范围内（±10~15%，InnoDB 自身同样有波动）。

## 剩余差距的原因（已验证）
`EXPLAIN` 显示 InnoDB 对 `SELECT SUM(id) ... FORCE INDEX(k_grp)` 是 **`Using index`（覆盖索引，不回表）**，
MyEngine 是 `NULL`（每行回表并拷贝整行）。下一步：支持覆盖索引扫描（`HA_KEYREAD_ONLY`），需要在二级索引里
保存可还原的键值（`Field::make_sort_key` 对字符串不可逆）。另外 MyEngine 对该查询的行数估计是 10（实际 500），
`records_in_range` 也该实现。

## 测试工具的修正
`compare_innodb.sh` 之前在 mysqld 没起来时会因"两边都是同一条连接错误"而误报 PASS；现已加守卫（连接错误或输出过短则失败）。

# 第四轮：行锁 + MVCC + 事务之后

环境、数据、参数与前几轮相同；同机噪声约 ±10~15%。完整数据见 `scripts/bench.py` 输出。

| 负载 | 并发 | 事务化前 MyEngine | 事务化后 MyEngine | 变化 | InnoDB(同轮) |
|---|---|---|---|---|---|
| 点查 | 1 | 4324 | 4402 | +2% | 4177 |
| 点查 | 4 | 15514 | 14536 | -6% | 15163 |
| 范围 100 行 | 1 | 1458 | 1490 | +2% | 1554 |
| 范围 100 行 | 4 | 4720 | 4234 | -10% | 4735 |
| 二级索引扫描 | 1 | 995 | 745 | -25% | 2432 |
| 二级索引扫描 | 4 | 3716 | 3093 | -17% | 10271 |
| 插入(自动提交) | 1 | 6683 | 1612 | **-76%** | 1326 |
| 插入(自动提交) | 4 | 15788 | 3741 | **-76%** | 3496 |
| 90%点查+10%更新 | 1 | 4634 | 3258 | -30% | 3124 |
| 90%点查+10%更新 | 4 | 12534 | 11037 | -12% | 12689 |

## 解读
- **读路径基本持平**（点查、范围扫描在噪声范围内）。二级索引扫描慢了 17~25%，多出来的是每行的可见性判断、
  版本链解引用和二级索引条目核对；**尚未做 profile，原因未验证**。
- **写路径大幅变慢，但原因主要不是 MVCC 而是 binlog**：引擎变成事务引擎后，每次自动提交都走 binlog 提交，
  默认 `sync_binlog=1` 会每次 fsync（InnoDB 同样付这个代价）。已验证：
  | 插入 c=1 / c=4 | `sync_binlog=1`(默认) | `sync_binlog=0` |
  |---|---|---|
  | MyEngine | 1388 / 2933 | **4893 / 10701** |
  | InnoDB | 1138 / 3291 | 2961 / 8562 |
  在两边付同样 fsync 代价时 MyEngine 与 InnoDB 基本持平；去掉 fsync 后 MyEngine 仍比事务化前慢约 25%
  （事务开始/提交、行锁、purge 队列的开销）。此前"插入比 InnoDB 快 4 倍"只是因为没有事务，不是实现更优。
- **内存**：对 1000 行做 30 万次更新，稳态下每 10 万次更新 RSS 仅增长约 5MB（purge 在跟上）；
  长事务固定住历史快照期间，同样的 10 万次更新多涨了约 53MB，符合预期。事务结束后 RSS 没有回落，
  这是 Go 运行时惰性归还内存，不能据此判断 purge 是否回收（回收的正确性由单元测试 `TestPurge` 验证）。

# 第五轮：间隙锁 + 去掉全局数据锁（物理并发）

## 方法
SQL 压测（`scripts/bench.py`）在 4 核机器上客户端自己就占了两个核，mysqld 已经吃满，**量不出锁竞争**。
所以另外写了绕开 MySQL 和 cgo 的**引擎核心并行基准**（`go/bench_test.go`，`go test -bench Engine -cpu 1,2,4`），
只测引擎内部的锁竞争。SQL 层的前后对比则用 `scripts/ab_compare.sh` 在同一时间、同一台机器上并排跑
（机器噪声 ±10~30%，不同时间点测出的数字不可比）。

## 引擎核心（ns/op，越小越好；1/2/4 核）
| 负载 | 改造前（全局读写锁） | 改造后 | 4 核对比 |
|---|---|---|---|
| 点查 | 1679 / 763 / 339 | 1927 / 850 / 359 | 慢约 6% |
| 范围扫描 100 行 | 6783 / 4462 / 4866 | 15233 / 8885 / **4217** | 快 13%；**单核慢约 2 倍** |
| 插入 | 15102 / 9804 / 9450 | 10254 / 10935 / **7288** | 快 23% |
| 更新不同行 | 16637 / 13183 / 11739 | 18091 / 10914 / **7869** | 快 33% |
| 90% 读 + 10% 写 | 3851 / 4057 / 3701 | 5115 / 2758 / **1710** | **快 2.2 倍**；扩展倍数 1.0 -> 3.0 |
| 二级索引扫描 100 行 | 195000 / – / 42200 | 176541 / 94079 / 43405 | 持平 |

## SQL 层（`sync_binlog=0`；MyEngine 改造前 -> 改造后，QPS）
| 负载 | c=1 | c=2 | c=4 |
|---|---|---|---|
| 点查 | 3702 -> 4170 (+13%) | 6501 -> 8041 (+24%) | 11993 -> 17027 (+42%) |
| 插入（自动提交） | 4014 -> 4754 (+18%) | 7865 -> 8229 (+5%) | 8328 -> 10546 (+27%) |
| 更新不同行 | 2952 -> 3575 (+21%) | 6974 -> 7302 (+5%) | 6845 -> 9687 (+42%) |
| 90% 点查 + 10% 更新 | 4124 -> 4072 (-1%) | 7527 -> 7688 (+2%) | 14775 -> 13347 (-10%，噪声内) |

扫描类（二级索引扫描、范围扫描）在同时间并排 A/B 里与改造前**在噪声范围内一致**
（二级索引扫描 c=1：改造前 665/656 对 改造后 678/613；c=4：2366/2520 对 2383/2116）。

## 过程中的两次"以为变慢了，其实不是/不全是"
1. 第一次 SQL 压测里二级索引扫描显示 -19%~-24%，**但那是负载顺序造成的混淆**：新版本插入更快，表因此长得更大，
   每次扫描要扫更多行。改成全新数据、扫描最先跑之后，才得到可比的数字。
2. 改成同口径后仍然慢了 26%~40%，这次是真的。用 `scripts/ab_compare.sh` 对 4 个提交并排测，定位到**几乎全部发生在 B1**
   （只换了树、引擎还是全局锁），原因是二级索引读一行要多约 4 对读锁操作。把批量预取扩展到二级索引的键之后消除了。
   如果当时只看 B2 之后的数字，会误以为是"去掉全局锁"造成的。
