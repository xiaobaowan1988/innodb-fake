# 已知的并发逻辑问题（未修复）

复现：`scripts/concurrency_check.py --socket /tmp/my.sock`（同样的并发负载在 InnoDB 与 MyEngine 上各跑一遍）。
8 个并发客户端，MySQL 8.0.40：

| 检查项 | InnoDB | MyEngine |
|---|---|---|
| T1 丢失更新：8×500 次 `UPDATE n=n+1`，期望 4000 | 4000 | **2756** |
| T2 UNIQUE 竞争：8 个客户端抢同样的 v（低压力） | 无重复 | 无重复（未触发） |
| T2 加压：6 轮 × 8 客户端 × 2000 个 v，被破坏的 UNIQUE 值个数 | 未测(0 预期) | **31**（每轮都有，行数比期望多 2~8） |
| T3 二级索引扫描行数应恒为 1000（并发单行更新索引列） | 0 / 9697 次异常 | **1545 / 13129 次异常**（出现过 996~1002） |
| T3b/c 更新结束后主/二级索引行数 | 1000 / 1000 | 1000 / 1000（静止后一致） |
| T4 并发 AUTO_INCREMENT：8×300 次插入，期望 0 报错 / 2400 行 | 0 / 2400 | **340 个重复主键报错 / 2060 行** |

## 原因（对应代码）
1. **没有跨连接的表级互斥。** `thr_lock_init(&lock)` 在 `ha_myengine::open()` 里，而 `lock` 是 handler 对象的成员，
   每个连接各有一份，根本没有共享。Go 端的 `RWMutex` 只保证单次调用原子，保护不了"读 -> 改 -> 写"这样的多步语句。
   → T1 丢失更新、T4 自增 id 重复分配（`get_auto_increment` 读最大值和随后的写入之间没有互斥）。
2. **UNIQUE 检查与写入是两步。** `unique_conflict()`（一次游标查找）和随后的 `MyEngine_Put` 之间没有任何保护；
   二级索引条目的键是 `索引键+主键`，Put 本身不会发现唯一键冲突。 → T2。
3. **多索引写入不是原子的。** `write_row/update_row/delete_row` 对主索引和每个二级索引分别调用 Go，每次独立加解锁。
   并发读者可能看到"主索引有而二级索引还没有"，或"旧、新二级索引条目同时存在"。 → T3。
   （读者遇到二级索引条目对应的行不存在时返回 `HA_ERR_KEY_NOT_FOUND`，MySQL 会把它当作扫描结束，行数会偏少。）
4. 没有事务：`ROLLBACK` 不撤销任何东西；多行语句中途失败会留下部分结果。

## 可能的修法（由小到大）
- **共享表级 THR_LOCK**（MyISAM 的做法）：以表名为键维护带引用计数的共享结构，所有 handler 实例用同一个 `THR_LOCK`，
  写语句独占、读语句共享。一处改动即可同时解决 T1~T4，代价是写与读在语句级互斥。
- **Go 端提供原子的多索引操作**（一次调用在一把写锁内完成主索引 + 全部二级索引 + 唯一性检查），
  解决 T2、T3，但仍不能解决 T1（读改写跨越多次调用）。
- **行锁 / MVCC 与事务**：才是 InnoDB 的做法，工作量最大。
