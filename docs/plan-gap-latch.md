# 计划：间隙锁（next-key 锁）+ B+ 树物理并发

> 规则：**代码与本计划不一致时，先改计划再改代码。** 文末有"变更记录"和各阶段的完成勾选。
> 前置：`docs/plan-mvcc.md`（行锁、MVCC、事务）已完成。本计划解决 `docs/concurrency-issues.md` 里遗留的前两条限制。

## 0. 目标与非目标

**目标**
1. **间隙锁**：RR / SERIALIZABLE 下，加锁读（`FOR UPDATE/SHARE`、`UPDATE`、`DELETE`、SERIALIZABLE 的普通读）扫描过的区间
   不再允许别的事务插入新行（防幻读）。验收：同样的场景在 InnoDB 与 MyEngine 上"谁被阻塞、读到几行"逐行一致。
2. **物理并发**：去掉"一把全局读写锁保护所有 B+ 树"。同一棵树上落在不同叶子的操作可以并行；
   只有节点分裂/合并（SMO）这类少数操作需要独占。验收：行为与现在完全一致（全部回归测试通过，`-race` 通过），
   并用压测量出多核下写入/读取的吞吐变化。

**非目标**
- 不做持久化、XA、外键、在线 DDL。
- 间隙锁只在 RR / SERIALIZABLE 生效；READ COMMITTED 不加间隙锁（与 InnoDB 一致）。
- 不模拟 InnoDB 的"页面边界/supremum 记录"这类物理细节，用**键区间**表示间隙（见 2.1）；
  边界处的个别差异会记录在文档里。
- 不做无锁/乐观版本校验读（Go 里读 slice 头的数据竞争会读到撕裂值，不安全）。

## 1. InnoDB 的目标行为（要对齐的语义）

加锁读在 RR 下扫描索引 I 时：
| 情形 | 加什么锁 |
|---|---|
| 唯一索引、给全了所有列的等值查找，**命中**一行 | 只有记录锁，无间隙锁 |
| 唯一索引等值查找，**未命中** | 只在"该键所在的间隙"上加间隙锁（不锁邻居记录） |
| 范围扫描 / 非唯一等值 / 唯一索引前缀 / 全表扫描 | 对扫描到的每个索引条目加 next-key 锁（记录 + 它前面的间隙） |
| 扫描终止处（第一个超出范围的条目，或索引末尾） | 只对它前面的间隙加间隙锁，**不锁该记录** |
| 通过主键位置回表（`rnd_pos`） | 只有记录锁 |
- 二级索引扫描：二级索引条目上加 next-key 锁，同时对聚簇记录（主键行）加记录锁。
- **插入**：对新条目要插入的每一个索引（主键 + 每个二级索引），若该位置落在**别的事务**持有的间隙锁内，必须等待
  （插入意向锁）。间隙锁之间互不冲突；间隙锁只会阻塞插入。
- 间隙锁到事务结束才释放。

## 2. 设计

### 2.1 用"键区间"表示间隙
- 每个索引（主索引或二级索引）有一个间隙锁表：`[]*gapLock{txn, lo, hi, loInf, hiInf}`，表示**开区间 (lo, hi)**，
  `loInf/hiInf` 表示无穷。键空间是"索引条目键"：主索引是主键编码，二级索引是 `二级索引键 + 主键`。
- 区间不依赖物理记录是否还存在：purge 删掉墓碑记录不影响已登记的区间（InnoDB 需要"间隙继承"，这里天然成立）。
- **合并**：同一事务在同一索引上连续扫描产生的相邻区间（新区间的 lo == 上一区间的 hi）合并成一个，避免线性增长；
  已被自己的区间完全覆盖的新区间直接跳过。相邻区间之间的单点（条目本身）由记录锁保护，所以合并是安全的。
- 插入冲突判定：新条目键 E 与别的事务的区间 (lo, hi) 冲突 ⇔ `lo < E < hi`。冲突时等待持有者事务结束，然后整体重试。

### 2.2 游标如何登记间隙（`Cursor`）
仅当 `事务隔离级别 ∈ {RR, SERIALIZABLE}` 且 `加锁模式 ≠ 无` 时才进入"间隙模式"。对每个候选条目 e：
1. 在"可以保证没有并发插入进入这个索引"的临界区内（见 2.4）找到候选 e 和它的物理前驱 pred（正向扫描）/后继 succ（反向扫描）。
2. 判断 e 是否已经**超出扫描范围**：
   - `seekExact`/前缀匹配扫描：e 不再以查找键为前缀；
   - 范围扫描：e 超过 `end_range`（MySQL 在 `handler::end_range` 里给出终点，C++ 编码后通过 `CursorBound` 传给 Go）；
   - 找不到候选（到了索引末尾）：视为超出，间隙是 `(最后一个条目, +∞)`。
   超出范围 → 只登记间隙 `(pred, e)`（反向则 `(e, succ)`），**不锁 e 的行**，返回"没有更多行"。
3. 否则登记 next-key：间隙 `(pred, e)` + 对 e 的主键行加记录锁（现有行锁逻辑，可能阻塞）。
4. 特例：唯一索引、全键等值（C++ 通过 `flags` 告知）：命中且行存在 → **不登记间隙**；未命中/行已删 → 只登记围绕该键的一个间隙。
5. 行锁等待发生在**释放索引临界区之后**；醒来后若行已被删则继续取下一个候选。
6. 事务结束时一次性移除该事务在所有索引上登记的区间，并唤醒等待者。

### 2.3 插入侧（插入意向）
`Insert/Update` 在真正发布新条目之前，对**每一个将新增的物理条目**（主索引：键不存在时的新主键；二级索引：不存在的
`键+主键` 条目）检查间隙冲突。有冲突 → 释放所有临时资源，等待冲突事务结束，整体重试。
等待加入等待图，参与死锁检测（经典的"两个事务都先对同一空洞 `FOR UPDATE` 再各自插入"会得到 1213，与 InnoDB 一致）。

### 2.4 原子性：登记间隙 vs 插入（物理并发改造后依然成立的协议）
每个索引一把读写锁 `gapMu`：
- **发布者（插入新条目）**拿 `gapMu` 读锁：在其内完成"检查间隙冲突 + 发布条目"。多个发布者可并行。
- **登记者（游标）**拿 `gapMu` 写锁：在其内完成"定位候选/前驱 + 登记区间"。
→ 登记与发布互斥，因此不会出现"我登记之前的检查通过、登记之后你才插入"的幻读漏洞，也不依赖全局锁。
只有 RR/SERIALIZABLE 的加锁范围扫描会拿写锁；主键等值命中、快照读、RC 完全不碰它。

### 2.5 B+ 树物理并发（两级锁：SMO 锁 + 叶子锁）
```
BTree.smo  sync.RWMutex   共享：任何普通操作；独占：节点分裂/合并/借位/根变化（SMO）
node.mu    sync.RWMutex   仅叶子：保护该叶子的 keys/vals，以及叶子上的行版本链
node.ver   uint64         叶子上每次增/删键自增（在 node.mu 写锁内）
BTree.epoch uint64        每次 SMO 自增（在 smo 写锁内）
```
- **内部节点只在 SMO 时修改**（分隔键只会在分裂/合并/借位时变），所以持有 `smo` 读锁时下降**不需要任何内部节点锁**。
- **普通插入/删除**：`smo.RLock` → 下降到叶子 → `leaf.Lock` → 叶子能容纳（插入：`len < maxKeys`；删除：`len > minKeys` 或叶子是根）
  就地修改后返回。否则释放叶子和 `smo` 读锁，改拿 `smo.Lock`，用现有的递归分裂/合并代码重做一遍。
- **读/定位**：`smo.RLock` → 下降 → `leaf.RLock`。跨叶子时**先放当前叶子锁再取邻居叶子锁**（任何时刻最多持有一个叶子锁，
  所以不会出现读写交叉造成的死锁）。非根叶子永远不会为空（删除快速路径要求删后仍 ≥ minKeys）。
- **游标**保存 `(叶子, 下标, 叶子 ver, 树 epoch)`：epoch 和 ver 都没变 → O(1) 沿叶子走；否则按上次的键重新下探。
- **版本链受所在主索引叶子的锁保护**：读者在叶子读锁内遍历链；写者（压入版本、回滚弹出、purge 修剪）在叶子写锁内修改。
  因此树提供"在叶子锁内执行回调"的原语：`GetFn / Modify / Upsert / DeleteIf`，回调必须短且不得阻塞。
- 带回调时**不嵌套持有两棵树的锁**：二级索引定位到条目后先放锁，再去主索引取行。

### 2.6 其他共享状态的拆分
- 引擎级 `e.mu` 只保护 `tables` 映射（DDL/打开表），不再出现在数据路径上。
- **行锁表分片**（64 个分片，按 `(表, 主键)` 哈希）；死锁检测的等待图用一把独立的小锁 `dmu`（只在要阻塞时才拿）。
- **唯一二级索引的"检查+发布"**用条纹互斥锁（按 `(表, 索引, 唯一键)` 哈希到 256 个互斥锁）串行化同一唯一键的并发插入，
  不同键并行。
- **purge** 不再靠全局写锁：对每个待清理的主键先**尝试**加行 X 锁（拿不到就留到下次），拿到后在叶子写锁内修剪版本链、
  再删除不再被引用的二级索引条目。这同时保证它不会和并发写者/回滚竞争。
- **回滚**：回滚事务在放行锁之前持有这些行的 X 锁，所以没有并发写者；在叶子写锁内弹出版本，必要时删除空链的键。
- 所有读者必须容忍"链为空（`head == nil`）的头"（回滚弹出和删除键之间的短暂窗口）：当作"不存在"。

### 2.7 加锁顺序（新）
```
行锁(lm 分片) →（释放行锁等待前不得持有下面任何一项）
唯一键条纹锁（按下标排序）→ 各索引 gapMu 读锁（按索引号排序）→ 树 smo 锁 → 叶子锁
游标：gapMu 写锁 → 树 smo 读锁 → 叶子读锁
e.tmu、dmu、pmu 都是叶子锁，内部不再取别的锁
```
等待（行锁、间隙冲突、唯一键冲突）一律发生在**释放条纹锁/gapMu/树锁之后**。

## 3. C++ / cgo 接口改动
- `MyEngine_CursorSeekFetch(..., flags, ...)`：`flags` 位 0 = "唯一索引全键等值"（C++ 判断：`HA_READ_KEY_EXACT` 且键列全给且索引 `HA_NOSAME` 且键不含 NULL）。
- 新增 `MyEngine_CursorBound(cur, kind, key, klen, inclusive)`：`kind` 0 清除、1 前缀（必须仍以 key 为前缀）、
  2 正向终点、3 反向终点。C++ 在 `index_read_map(EXACT)` 后设前缀边界（供 `index_next_same` 使用），
  在 `end_range` 非空时编码并设终点边界（先于首次定位设置，因为首个候选也可能已越界）。
- 其余接口不变。

## 4. 测试计划
1. **Go 单测（`-race`）**：间隙冲突判定与合并；插入意向等待/重试；经典死锁；唯一命中不登记间隙；越界只登记间隙不锁行；
   RC 不登记；`FOR UPDATE` 扫描 + 并发插入后重复读行数不变。
2. **树并发单测（`-race`）**：并发插入/删除/查找/游标与排序切片对照；高频分裂/合并（小 `maxKeys`）；
   多读者 + 多写者 + SMO 混合；游标在并发修改下始终返回"当前键之后最近的存活键"。
3. **SQL 场景（`scripts/txn_check.py` 增量，InnoDB 对照）**：范围 `FOR UPDATE` 后在范围内/边界/范围外插入；唯一等值未命中；
   非唯一二级索引等值；全表扫描 `DELETE`；二级索引范围 + 插入新键/更新键进入范围；SERIALIZABLE 普通读；
   RC 不阻塞；supremum（`id > 最大值`）；重复读行数不变；经典间隙锁死锁；反向扫描。
4. **回归**：`compare_innodb.sh`（147 个结果集）、`concurrency_check.py`（四项为 0）、`txn_check.py` 原有 21 个场景、`go test -race`。
5. **性能**：重跑 `bench.py`；增加"多线程写同一张表不同行"的负载量化物理并发的收益；对比 SMO 次数。

## 6. 风险
- **边界差异**：InnoDB 的间隙以页内记录为单位，且对"范围终止记录"的处理随版本有差异。以 MySQL 8.0.40 的 InnoDB 为对照做实验，
  个别差异记录在文档里而不是硬凑。
- **正确性比性能重要**：物理并发改造是最容易引入隐蔽竞争的部分。对策：先有完整的回归和 `-race` 安全网；
  先改树、再改引擎，两步之间都跑全套测试；每个关键不变量做"故意改坏"的变异检查。
- **RWMutex 的写者优先**会让"已持读锁的 goroutine 再次取读锁"死锁：约定同一 goroutine 不嵌套同一把读写锁的读锁。
- **SMO 期间的停顿**：分裂/合并会短暂独占整棵树；分裂约每 16 次插入发生一次（`maxKeys=32`），先量化再决定是否需要更细的 SMO 并发。
- **等待图的陈旧边**：唤醒后必须清掉 `blockedOn`（已在 MVCC 阶段踩过）；新增的"等待事务结束"同样遵守。

  3. **A2 需要补上一个初稿遗漏的前提：`records_in_range`**。SQL 场景对照 InnoDB 发现 15 个里有 6 个不一致，且全是
     "MyEngine 锁得更多"。用 `EXPLAIN` 确认原因：InnoDB 对 `id BETWEEN 15 AND 35`、`k = 2`、`id > 40` 分别选
     `range`/`ref`/`range`，MyEngine 都选了 `ALL`（全表扫描，锁住所有间隙）——因为引擎没实现
     `handler::records_in_range`，优化器无法估算范围里的行数。锁的范围由执行计划决定，所以这不只是性能问题，
     必须先实现它才能做有意义的对照。
- v3（A2 对照实验后）：用 MySQL 8.0.40 的 InnoDB 做了 20 多组"哪些插入/更新被阻塞"的对照实验，得到下面这些**实测规则**
  （都已写进 `scripts/txn_check.py` 的场景里，作为回归）：
  1. **反向扫描**：对每个访问到的记录（含停止记录）锁它**前面**的间隙，起点（第一条记录）上方的间隙也锁；
     停止记录的行也被锁（MySQL 对反向扫描不设 `end_range`，停止记录会被返回再丢弃，所以自然被锁住）。
     初稿写的是"锁候选后面的间隙"，实验证明少锁了停止记录前面那一段。
  2. **起点规则**：范围以唯一索引的全键 `>= K` 开始且 K 恰好存在 → 这一条只加记录锁，不锁它前面的间隙。
     （`flags` 的"唯一全键"位因此也要用于 `HA_READ_KEY_OR_NEXT`，不止精确查找。）
  3. **终点规则**：唯一索引的全键、包含端点的终点 `<= K` 且 K 恰好存在 → 扫到 K 就结束，
     不再读它后面的记录，所以也不锁后面的间隙。（`CursorBound` 增加"唯一"标志，Go 端命中后让下一次 `Step` 直接返回结束。）
     终点为开区间或终点值不存在时，行为与初稿一致（只锁间隙，不锁停止记录的行）。
  4. **正向停止记录**只锁间隙、不锁行（`UPDATE` 停止记录不阻塞）——与初稿一致。
  5. **已知且接受的差异**：二级索引范围扫描的停止条目，InnoDB 还会锁它的**记录部分**（实测：
     `WHERE k BETWEEN 2 AND 3 FOR UPDATE` 之后 `UPDATE ... SET k=9 WHERE id=<停止条目的行>` 被阻塞），
     我们只锁间隙。这只是少锁一点（并发略高）：范围内的幻读仍由间隙锁完全防住，停止条目移入范围会撞上间隙锁。
     不实现二级索引条目的记录锁。
  6. **`records_in_range` 是前提**（见 v2）。

- v7（并发逻辑审计：用户问"现在的并发逻辑是不是有问题，先不考虑速度"）：
  **方法**：不靠推理下结论，把可疑点逐个做成和 InnoDB 的对照实验。实测**没有问题**的：S→X 升级死锁（恰好一个 1213）、
  8 个客户端并发 `INSERT … ON DUPLICATE KEY UPDATE` 计数（3200/3200）、并发修改主键（主索引/二级索引行数一致且无重复）、
  同事务内 DELETE 再 INSERT 同一键 + 快照读者（任何快照里行数恒定）、并发负载结束后没有任何残留的行锁/间隙锁。
  **发现两个真实问题**：
  1. **语句起点被重复重设**。显式事务里 `INSERT (20),(21),(1)`（最后一行重复）失败：InnoDB 整条语句撤销，
     本引擎残留 `main=[1,20,21]`、`audit=[1,20]`（AFTER INSERT 触发器写入 audit 表）。
     修法：语句起点只在"这条语句的第一个表被打开时"设置一次；用 MySQL 的语句结束钩子（`hton->commit/rollback` 的 `all=false`，
     每条语句结束都会被调用）清除"语句进行中"标记。`start_stmt`（LOCK TABLES 模式）同样走这条路径。
     不用 `external_lock(F_UNLCK)` 做计数：LOCK TABLES 模式下它不会逐语句调用，计数会泄漏，泄漏的后果是语句回滚范围过大
     （把前面语句的修改也撤销掉）——比不修更糟。事务结束时一并清除标记。
  2. **锁等待不可被 KILL**。`KILL QUERY` 一个被行锁阻塞的语句：InnoDB 立即返回 1317，本引擎 8 秒后仍在阻塞（只能等 50 秒超时）。
     修法：C++ 把 `thd_killed` 的函数指针和 `thd` 交给 Go 的事务；所有等待（行锁、间隙冲突、唯一键）改成每 100ms 醒来检查一次，
     被杀则退出并返回新的错误码 `rcKilled`；C++ 按 InnoDB 的做法 `thd_set_kill_status(thd)` 后返回 `HA_ERR_GENERIC`。
     用 C 里的一个小跳板函数调用函数指针，避免 Go 库对 `thd_killed` 产生链接期的未定义符号。
  **回归测试**：`scripts/txn_check.py` 增加触发器场景（成功路径、触发器内部失败、显式事务里的语句回滚）和 KILL 场景，与 InnoDB 逐行对照。
  **修复结果**（v7 的两个问题）：
  - 语句起点：`Txn` 增加 `inStmt`；`StmtBegin` 只在语句的第一个表打开时生效，`StmtEnd`（由 `hton->commit/rollback` 的 `all=false`
    钩子调用）才结束一条语句。新增 `MyEngine_TxnStmtEnd`。触发器场景（成功路径、触发器内部失败）与 InnoDB 逐行一致，
    且"同一事务里前面成功的语句不会被后面失败语句的回滚误撤销"也被验证。
  - KILL：`Txn.waitOn` 统一所有等待（行锁、间隙冲突、唯一键），每 100ms 检查一次 `thd_killed`；`MyEngine_TxnSetKill` 通过 C 跳板调用
    C++ 传入的函数指针。`KILL QUERY` 阻塞的语句在 InnoDB 和本引擎都立即返回 1317，连接和对方事务不受影响。
  - 变异检查：嵌套 `StmtBegin` 重设起点、等待不检查 KILL、KILL 不轮询——三个都被新增的 Go 单测抓到。
  - 回归：`go test -race -count=2`、216 个结果集、55 个场景（新增 3 个）、并发检查、锁超时与死锁场景全部通过。
  - 新增 `scripts/concurrency_audit.py` 保留审计时用的探针（S→X 死锁、ODKU 并发、并发改主键、删除再插入的快照一致性、残留锁探测）。
  **没有发现问题的审计项**也如实记录在上面 v7。
  **审计的局限**：只测了我想到的场景。没有覆盖的包括：LOCK TABLES 模式下的语句起点（`start_stmt` 与钩子的交互）、外键、
  存储过程里的游标在同一事务内读自己刚写的行（批量预取对"读到自己后来的修改"是异步的，InnoDB 的游标本来也是 asensitive）。
- v8（第二轮并发逻辑审计：用户问"现在还有逻辑问题吗"）：
  **方法**：把第一轮审计里自己承认"没覆盖"的区域，加上这次想到的 InnoDB 行为，逐个做成对照实验。
  **没有问题**（与 InnoDB 一致）：`LOCK TABLES` 模式下带触发器的语句失败后的原子性、`KILL CONNECTION`、`ALTER TABLE`
  （加列/加删索引/唯一键，行数与索引行数一致）、多表 `UPDATE/DELETE`、跨引擎事务（InnoDB + MyEngine 同一事务的 ROLLBACK/COMMIT）。
  **发现 4 个真实问题**：
  1. **锁队列不公平，写者可能被饿死**。A 持有 S 锁，B 请求 X 锁（等待），C 再请求 S 锁：InnoDB 让 C 排在 B 之后，
     本引擎让 C 直接插队拿到。持续有人 `FOR SHARE` 读同一行时，写者永远拿不到锁。
     修法：行锁请求按到达顺序排队。新请求除了被冲突的**持有者**阻塞，还被排在它前面的、与它冲突的**等待者**阻塞。
     等待者的队列位置在被唤醒后保持不变（唤醒后重新判断，不是重新排到队尾）；等待者退出（超时/被 KILL/死锁牺牲者）时必须唤醒
     同一把锁上的其他等待者，否则排在它后面的会一直睡下去。等待图的边要包含"前面的等待者"，这样环能被检测到。
     **例外：锁升级（已持有 S 再请求 X）不排队**，只被其它持有者阻塞——否则"A 持 S，B 等 X，A 升级 X"会被我们人为地制造成死锁。
     （InnoDB 在这种情形会报死锁 1213，本引擎会让 A 升级成功；这是有意的差异，结果更宽松且不会饿死。）
  2. **`SELECT … FOR UPDATE NOWAIT / SKIP LOCKED` 不生效**，都一直阻塞。策略由 `store_lock` 里的
     `table->pos_in_table_list->lock_descriptor().action`（`THR_NOWAIT` / `THR_SKIP`）给出。
     修法：游标带等待策略（只对加锁读生效）；行锁请求需要等待时：NOWAIT 返回新错误码，C++ 按 InnoDB 的做法
     `my_error(ER_LOCK_NOWAIT)` 并返回 `HA_ERR_NO_WAIT_LOCK`；SKIP LOCKED 则跳过这一行继续取下一行。
  3. **`START TRANSACTION WITH CONSISTENT SNAPSHOT` 的快照没有在那一刻建立**（读到了之后别人提交的值）。
     之前把它列为非目标，现在发现实现很小：实现 `hton->start_consistent_snapshot`，在 RR 下立即创建事务并建立视图。
  4. **外键被静默忽略**：`CREATE TABLE … FOREIGN KEY` 成功，插入孤儿行也成功（InnoDB 报 1452）。这是静默的数据完整性丢失，
     比"不支持"更糟。修法：`create()` 里发现表定义含外键就拒绝建表（`ER_ILLEGAL_HA_CREATE_OPTION`）。
     （这是与"静默忽略外键"的 MyISAM 式行为不同的有意选择。）
  **回归测试**：`txn_check.py` 增加队列公平、NOWAIT、SKIP LOCKED、一致性快照场景（与 InnoDB 对照）；
  外键拒绝与锁升级例外没有 InnoDB 可对照，放在 Go 单测和 `concurrency_audit.py` 的断言里。
  **修复结果**（v8 的 4 个问题）：
  1. 队列公平：行锁等待队列按到达顺序；等待者唤醒后保持位置（`wakeAll` 关闭并替换它的 channel）；放弃/死锁牺牲者离开时唤醒后面的等待者；
     锁升级不排队；purge 的 `tryLock` 在有人排队时让路。Go 单测：FIFO、写者不被重叠的读者饿死、升级不被人为造成死锁、
     放弃后唤醒后面的等待者。4 个变异检查（插队、升级也排队、放弃不唤醒、SKIP 不跳过）全被抓到。
     **与 InnoDB 的有意差异**：A 持 S、B 等 X、A 升级 X——InnoDB 报死锁，本引擎让 A 升级成功。
  2. NOWAIT / SKIP LOCKED：游标带等待策略，`GetRowPolicy` 同理；`CursorOpen`/`GetRow` 的 cgo 接口各增加一个参数。
  3. 一致性快照：`hton->start_consistent_snapshot` + `MyEngine_TxnSnapshot`（RR/SERIALIZABLE 下立即建立视图）。
  4. 外键：**服务器对没有 `HTON_SUPPORTS_FOREIGN_KEYS` 的引擎，在调用 `create()` 之前就把外键从表定义里丢掉了**，
     所以最初写的"检查 dd 表定义里的外键"是死代码（实测外键仍被接受）。引擎唯一能看到外键子句的地方是当前语句的
     `thd->lex->alter_info->key_list`（`KEYTYPE_FOREIGN`），现在改成检查它；建表和 `ALTER TABLE ADD FOREIGN KEY` 都返回 1478。
     这依赖服务器内部结构，换 MySQL 版本可能要调整。
  **回归**：`go test -race -count=2`、216 个结果集、59 个场景（新增 4 个）、并发检查、`concurrency_audit.py`（含外键断言）、
  锁超时与死锁场景全部通过；引擎核心基准无明显变化。

       本引擎只留下重复行的主键 S 锁，没有二级唯一索引上的间隙锁。重复错误本身仍可重复（行被锁住），
       只是并发上更宽松，不破坏隔离。接受为已知差异。
    6. **真问题（待修）seeds 4、9**：主键重复导致 INSERT 失败时，本引擎保留的是已存在行上的 **X** 锁，InnoDB 保留的是 **S** 锁。
       后果：第二个同样会重复的 INSERT 在本引擎里被无谓阻塞（InnoDB 里 S 与 S 兼容，直接报 1062 / IGNORE 忽略）。
       最小复现：S3 `BEGIN; INSERT (10,..)`（pk 10 已存在，1062）；S2 `INSERT (10,..)`。
       修复：`Insert` 发现主键上已有活行且此前不持有该行锁时，把刚取的 X 降级为 S（新增 `lm.downgrade`）。
    7. 最小化后归类：seed 8 = 行锁是整行粒度而 InnoDB 按索引条目加锁（本引擎的重复检查会等整行锁，InnoDB 不等），接受；
       seed 7 = 同第 4 条（唯一二级索引重复错误的 S next-key 间隙锁，NULL 插入被挡），接受；seed 10 = 同第 2 条（插入顺序），接受。

       handler 实现 `unlock_row()`；仅在 RC（及 RU）下生效；遇到已删除的行且锁是新取的，RC 下直接放掉。RR/SERIALIZABLE 保持不放。

          别人删它会被挡；本引擎什么都不留，别人可以删掉它并提交，本事务重试同一个 INSERT 就成功了（重复错误不可重复）。
          修复：`DupError` 带上冲突行的主键；`Insert`/`Update` 遇到它时（持有本行 X 锁、释放唯一条纹锁之后）对该行取 S 锁并重查，

## v10：唯一二级索引条目级行锁（消除"整行锁 vs 索引条目锁"的差异）

**动机**：v9 的差分模糊测试里，52/58/80/87/96 等 seed 的差异都来自同一件事——本引擎只有"主键行锁"，一把锁覆盖整行所有索引；
InnoDB 在每个索引条目上各加各的锁。后果：唯一键冲突检查要在冲突行的主键上取 S 锁，别人只改该行的非索引列也会被挡；
反过来，别人经主键扫描持有该行 X 锁时，本引擎的重复检查会无谓地等。

**范围（只做唯一二级索引，原因：只有它的条目锁会被"重复检查"这类操作单独持有）**：
1. 锁键泛化：`lockKey{tbl, idx, key}`。`idx=0` 就是原来的主键行锁；`idx>0` 的键是完整二级索引条目（索引键 + 主键）。
   `lm.lockEntry(t, tb, idx, entry, mode)` 是新入口，其余机制（FIFO、死锁检测、超时、kill、NOWAIT/SKIP）原样复用。
2. **重复检查只在冲突条目上取 S 锁**（不再锁整行主键）：`DupError` 带上索引键 `Key` 与主键 `Pk`，`holdDup` 锁 `(Idx, Key+Pk)`。
3. **写者在会改变的唯一条目上取 X 锁**（在主键 X 锁之后、唯一条纹锁之前，保证加锁顺序固定）：
   - `Delete`：旧行所有 `unique` 条目；
   - `Update`：旧行中"新行不再保留"的 `unique` 条目（唯一列被改、或主键被改时全部）；
   - `Insert` 的新条目不需要（没人持有它们，且未提交的条目由下面的版本链判断兜住）。
   这样 A 的重复错误 S 锁挡得住别人对该行的 DELETE/改唯一列，但挡不住只改非索引列的 UPDATE——与 InnoDB 一致。
4. **"等未提交者"改成按条目判断**：原来只要冲突行的链头是别的活跃事务写的就等；现在只在**该条目的成员状态是被未提交事务改变的**时候才等：
   沿版本链找到与链头"该条目是否存在"状态相同的最老版本，它的作者就是造成当前状态的事务；作者是别的未提交事务才等。
   只改非索引列的未提交更新不再让重复检查等待。等待改用 `waitTxn(holder)`（该事务只持有隐式锁，没有显式条目锁可等）。
5. 不做（列为残留差异）：经唯一/非唯一二级索引的**扫描**仍只锁主键行（InnoDB 还会锁扫到的索引条目，只有覆盖索引扫描才看得出差别）；
   非唯一二级索引条目没有条目锁。

**锁顺序**：行锁（主键）→ 条目锁（按索引下标升序）→ 唯一条纹锁 → gapMu → 树 → 叶子，不变；重复检查的 S 锁取在释放条纹锁之后。

**验证**：Go 单测（写者在条目上被挡/不被挡、等未提交者的判断、死锁不挂、变异检查）、SQL 场景（对照 InnoDB）、
把 v9 里那 5 个 seed 的最小复现加入回归、`-race`、`fuzz_diff.py` 重跑 0–99。

**v10 结果**：实现与计划一致（`lockKey{tbl,idx,key}`、`lockEntry`、`lockOldEntries`、`entryChanger`、`DupError{Idx,Key,Pk}`）。
Go 单测 `TestEntryLockGranularity`、`TestDupCheckWaitsOnlyForEntryChangers`（拿掉"写者锁条目"或"按条目判断等待"任一项都会失败）；
SQL 场景 63/63 与 InnoDB 一致（新增 `entry_lock_dup_error_only_blocks_indexed_changes`、`entry_lock_dup_check_ignores_pk_lock_holder`）；
216 个结果集、并发检查、`concurrency_audit.py`、`-race` 全部通过。
`fuzz_diff.py` seed 0–99：有差异的 seed 从 26 个降到 24 个；v9 里归为"整行锁 vs 条目锁"的 8、52、58、80、87、96 以及 35 都不再出现。
注意：fuzzer 对探测窗口（0.3s）敏感，个别 seed 在整批里有差异、单独重跑却一致（如 93、40），所以 seed 集合每次会有 ±几个的波动，不能当作确定性结论。
**仍然存在的差异**：插入顺序类（InnoDB 先插主键）、唯一键重复错误在二级唯一索引上的间隙锁、扫描经二级索引时不锁索引条目、
非唯一二级索引没有条目锁、死锁牺牲者选择。

## v11：全 RC / 全 RR 序列 seed 100–199 的发现

顺序重跑（不并行）：RR 32 个、RC 27 个问题 seed，首个差异绝大多数仍是已知的"插入顺序"类。
需要追的是"InnoDB 不阻塞、我们阻塞"的少数几条，最小化后得到一个真问题：

12. **主键变更的 UPDATE 撞上已有主键时留下 X 锁**：`UPDATE t SET id=8 WHERE id=2`（8 已存在）报 1062，
    InnoDB 只在 8 上留 S 锁；我们先对新主键取了 X，之后别人的 `INSERT IGNORE (8,..)`（要 S）被无谓阻塞。
    修法同 `Insert`：先不加锁看新主键是否有活行，有则取 S 并确认后报重复；否则取 X；竞态下降级。
    验证：单元测试 `TestUpdateToExistingPkKeepsOnlySharedLock`（回退修复应失败）+ txn_check 场景 + 差分重跑 seed 196。

13. **RC 下语句回滚后，被回滚的插入不留行锁**：`INSERT (5,..),(2,..)`（2 已存在）整条失败，InnoDB 在 RC 下没有残留，
    别人随后 `INSERT 5` 直接成功；我们的 `RollbackStmt` 保留了 5 上的 X 锁，把它挡住（seed 122 最小化）。
    RR 下 InnoDB 留有已删除标记的残留记录，别人仍被挡——这是已知差异的另一面，我们 RR 下保持现状（两边都挡）。
    修法：`Txn.fresh` 记录本语句里新取得行锁的插入；RC 下 `RollbackStmt` 撤销之后，凡是行已不属于本事务的就放锁。
    验证：单元测试 `TestRollbackStmtReleasesInsertLockUnderRC`（RC 放、RR 不放）+ txn_check 场景 + 差分重跑 seed 122。
